AWS Widgets: Forge migration and product decision

The current app is a legacy Connect macro that puts AWS credentials in the browser and stores encrypted credentials in a Confluence app property. A Forge migration is feasible, but it should be treated as a security-and-product decision, not a descriptor conversion.

Scope: repository evidence, existing migration patterns in conf-app and AsyncAPI, the live Marketplace partner view, Firebase lifecycle logs, the retained lifecycle sheet, and read-only Cloudflare HTTP traffic analytics. The evidence review is complete as of 28 August 2026. No production systems, customer content, or settings were changed.

Recommendation: do not perform a direct lift-and-shift, and do not production-roll out Forge yet. The evidence audit confirms an installed footprint and credible recent interaction from at least one external customer network, but still cannot prove a successful AWS resource result. Proceed with the smallest development-only Forge rebuild and a safe trust-model spike; keep production rollout behind outcome telemetry and customer validation. The rebuild must use a server-side credential model or customer-owned federation.
Implementation update — development only: the focused Forge rebuild is now implemented, registered in a dedicated developer space, deployed to the Forge development environment, and installed only on lite-dev.atlassian.net. Credentials use installation-scoped Forge secret storage; AWS SDK v3 calls run only in the resolver; EC2, S3, Lambda, ECS, and DynamoDB return allow-listed view models. Local verification passes 64 unit/component tests plus the Forge app contract, and an authenticated Forge manifest lint has zero errors. This does not clear the production gate: no real AWS success, customer migration, Marketplace adoption, or production deployment has occurred.

The decisive migration concern: credentials

Current behavior is not an acceptable Forge target. The front end receives an access key and secret key, initializes the AWS SDK in the browser, and calls AWS services from the viewer. The Connect code encrypts credentials with a key derived from public macro/site context; that is obfuscation, not a secure secret boundary. A Forge migration must not reproduce this browser-secret design.
ConcernCurrent behaviorRequired Forge design decision
Credential exposureAWS credentials are loaded into each macro viewer's browser.Choose either a vendor-managed server-side secret, or customer-owned short-lived federation. Do not send long-lived AWS keys to Custom UI.
Least privilegeThe UI recommends read-only access but cannot enforce an AWS policy.Publish supported resource types and minimum IAM policies; use assumed roles/scoped sessions where possible.
Data residency / egressBrowser talks to AWS directly; Firebase also hosts Connect lifecycle endpoints.Declare every remote and data flow. Forge permissions/egress must reflect the actual implementation, not an aspirational architecture.
Existing tenant settingsCredentials live in a Connect app property.Implemented a server-only, STS-validated import into Forge secret storage under the unchanged Connect key. Never emit secrets to the browser or logs.

How to unblock a build decision: obtain explicit customer-authorized validation from a small set of installed tenants, or add a separately reviewed, privacy-safe outcome signal before committing to migration. Classify installed, configured, successful view, and retained use separately. Do not recover or export AWS secrets, and do not contact customers as part of this read-only discovery.

For a proven narrow use case, the recommended architecture is a Forge Custom UI macro plus a resolver, with AWS calls delegated to a purpose-built gateway or federation exchange. The gateway returns only a resource view model needed by the macro; it never returns long-lived AWS credentials. The Forge resolver is the policy boundary: it validates macro context, performs only declared external work, and records safe outcome telemetry. The selected external component must use a per-tenant credential reference or short-lived role assumption, not a global shared AWS key.

Why this is deliberately smaller than Conf Mini-Sites: the Mini-Sites pattern is appropriate if AWS Widgets becomes a host for rich, user-created interactive dashboards. A single AWS resource card should not inherit an upload/publish/host-per-instance system just to render a status card. Share a foundation only after the product surface—not merely the framework—is shared.

Manifest direction — align to conf-app without copying it

The conf-app manifest is a useful discipline, not a template to copy. AWS Widgets should request the smallest Confluence scope set and declare only real remotes and operations. Copying conf-app's broad scope inventory would create unnecessary consent and review risk.

Open decisions

  1. Will the owner seek customer-authorized demand validation, make an explicit strategic build decision despite unknown active use, or proceed toward controlled retirement?
  2. Which AWS authentication model is acceptable to customers and security review?
  3. Is AWS Widgets a narrow cloud-status macro, or the seed of a broader interactive dashboard/mini-site product?
  4. Should the future app remain free, be paid, or be bundled—after usage evidence rather than by migration default?
  5. What customer communication and support capacity exists for a Connect retirement if active installs are discovered?
